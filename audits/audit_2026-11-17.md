## 3. Evidence from independent inspection

**3.1 Containers.** `docker compose ps`: api, db, redis, worker all `(healthy)`, up 2 hours. Ports bound to `127.0.0.1` only. api and worker run as user `app`, not root. Named volume `earnings-surprise-predictor_pgdata` exists.

**3.2 Fault tests (by hand, not scripted).** Stopping the worker: HTTP 503, `worker: error: no worker replied`. Also stopping Redis: HTTP 503, redis and worker report `ConnectionError`. Also stopping the database: HTTP 503, postgres reports `OperationalError`. After `docker compose up -d --wait`: HTTP 200, all four healthy. Observation: when Redis is down the worker check can report `OperationalError`, which is a broker error and not a database one. The label is misleading but the status is correct.

**3.3 Clean checkout and pinning (EQ-04).**
- A copy containing only the files git would include (no `.env`) fails `docker compose config` with the message "Copy .env.example to .env first" (exit 1). The guard works. The documented route is therefore two commands, and the README is empty, so the only documentation is comments in `docker-compose.yml`.
- `docker compose build --no-cache` from that copy: exit 0. Image 3.64 GB. `pip freeze` of the fresh image matched `requirements.lock` exactly (129 of 129 lines). This was resolved the same day, so it proves the build works today and not that it will work later.
- `requirements.txt`: 22 dependency lines, 0 use `==`. `torch` is installed in the Dockerfile with no version. Nothing fails the build on an unpinned dependency. EQ-04 requires exact pins and that failure. **FAIL.**
- `requirements.lock` holds the exact versions but the Dockerfile does not install from it. It is also not installable as is (`torch==2.15.0+cpu` needs the PyTorch CPU index, and the spaCy model is a URL).

**3.4 Secrets (SP-06).** No key-like strings (`sk-`, `hf_`, `AKIA`, private key headers) in the files git would include. `.env` is ignored and untracked. The only email-like strings in the repository are a university contact address in `data-requirements.md` and `library-enquiry-draft.md`. `SEC_USER_AGENT` reaches the containers from the shell and `/health` reports only whether it is set. No secret scanner runs in CI because no CI exists.

**3.5 Request logging (NFR-11).** A real request produced `INFO: 127.0.0.1:33410 - "GET /health HTTP/1.1" 200 OK`. There is no request identifier and no latency. **FAIL.**

**3.6 Database URL defect (found, no requirement ID).** `DATABASE_URL` is built as `user:password@db`. SQLAlchemy parses a password that contains `@` wrongly (password `p@ss` gives host `ss@db`, password `p`). Passwords containing `/`, `:` or `#` parsed correctly. Low severity for local development, but a real defect.

**3.7 CI and configuration.** None of `.github/`, `.gitlab-ci.yml`, `.pre-commit-config.yaml`, `pyproject.toml`, `ruff.toml` or `mypy.ini` exists.

## 4. Automated tests

Created in this audit: `tests/test_config.py`, `tests/test_health_unit.py`, `tests/test_stack_integration.py`, and `requirements-dev.txt` (pytest 9.2.0, ruff 0.17.5, exact pins). They run in a throwaway container on the compose network and are not in the application image.

Command:
```
docker compose run --rm --no-deps -v "$PWD/tests:/app/tests:ro" -v "$PWD/requirements-dev.txt:/app/requirements-dev.txt:ro" api \
  sh -c 'pip install --user -q -r requirements-dev.txt && python -m pytest -v -p no:cacheprovider tests'
```

| Result | Detail |
|---|---|
| **PASS** | 16 passed in 4.64 s (Python 3.12.16, pytest 9.2.0): 4 config, 7 health unit, 5 stack integration. |
| **Planted fault (worker stopped)** | `2 failed, 1 passed, 2 deselected in 22.80 s`: the health test and the Celery round-trip test failed as they should. This shows the integration tests can fail. |

Limits: the unit tests replace PostgreSQL, Redis and the worker with stand-ins, labelled as synthetic in the test file (SC-04). Coverage was not measured, so no coverage claim is made. The integration tests fail, not skip, when the stack is down.

## 5. Lint (ad hoc, because no configuration exists)

`ruff check` with default rules over `src/` and `tests/`: 13 findings. 10 are `EXE002` (file is executable with no shebang). They come from the Windows disk mount, where every file shows mode `-rwxrwxrwx`, so they are an environment effect and not a code defect. 3 are `BLE001` (blind `except Exception`) in `src/earnings/api/main.py`. These are deliberate, so the health check reports a failure instead of crashing, and each logs only the exception type. No type checker was run. EQ-02 stays FAIL because nothing is configured or enforced.
