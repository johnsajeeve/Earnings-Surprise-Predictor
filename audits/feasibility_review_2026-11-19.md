## 3. Can each requirement be implemented

Test classes used in the table in Section 5 (my judgement):

- **A**: an automated unit, integration or contract test can prove it.
- **B**: an automated repository, CI or configuration check can prove it (a scan, a static check, a file that must exist).
- **C**: it needs a measured run or a data experiment (benchmark, load test, hand-labelled sample, source spike). A test can check that the report exists and compares to the threshold. Whether it passes depends on real data or hardware, so it is not guaranteed.
- **D**: it needs a person or a process (sign-off, meeting, ethics approval, someone else running the build). A test can only check that the record exists.
- **U**: umbrella. It is met when its listed child requirements pass.
- **X**: not testable as written.

| Class | Count of 376 |
|---|---|
| A: automated test | 244 |
| B: repository or CI check | 49 |
| C: measured run or data experiment | 50 |
| D: person or process evidence | 30 |
| U: umbrella | 1 |
| X: not testable as written | 2 |

Only classes A and B (293) can be turned into code tests that always give a clear pass or fail. 50 (class C) have a result that depends on the real data or hardware. 30 (class D) cannot be proven by code. 2 cannot be tested as written.

63 requirements carry an issue flag from Section 4. No requirement was found to be impossible in principle. Several cannot be implemented or tested as written until a decision is made. They are listed below in the order I suggest we resolve them.

## 4. Issues, in suggested order of resolution

### Group 1: the wording contradicts another requirement or a decision (tests cannot be written yet)

**I-01 Prediction point (decision C-17, wording D-33 not applied).**

pipeline.md Section 2.2 shows that TX-02, FR-02, GATE-2, FR-22, FR-01 and FR-24 cannot all hold if text comes from the same quarter's call. John chose T0 (earlier calls only) as the headline and T1 as a separate nowcast (C-17), but the wording edits in D-33 are not applied. FR-01 criterion 3, FR-22 criterion 1, the FR-24 text rows and GATE-2 still read the old way, while FE-23, UX-06, SV-03, MD-02 and AG-07 already assume the new design. A test written to FR-22 as it stands would fail every T1 prediction by design. Related: FR-07 and FR-18 say a ticker needs four prior quarters, but FE-18 needs the last call plus four before it at T0 (five calls).

Affects: FR-01, FR-07, FR-18, FR-22, FR-24, ER-01, TX-02, GATE-2, FE-18, FE-21.

Resolution: John approves the D-33 wording (FR-01, FR-22, FR-24, GATE-2, new FR-29). I will add the five-calls point to the same change. Requirement text changes need John's approval and regenerate the three generated files.

**I-02 No free dated sector history (D-20), but Must requirements assume it.**

Data Section 5 says no free point-in-time GICS source was found. SRS-14 switches sector scoring off in that case, and SRS-01 to SRS-10 are "Must if built". But SEC-01, SEC-02 and VL-11 are plain Must, VL-02 and VL-03 replay sector features, and TX-07, IG-22, TR-04, FE-20, FE-31, SRS-13 and EQ-09 ask for reports "by sector". Using today's sector for those reports would break SEC-01 ("the current classification is never used for past events"). SRS-02 also says GICS, which the free route cannot give.

Affects: SEC-01, SEC-02, VL-11, VL-02, VL-03, TX-07, IG-22, TR-04, FE-20, FE-31, SRS-01 to SRS-14, EQ-09.

Resolution: Option A: run the 20-company SIC spike in D-20. If EDGAR gives dated SIC, map it to Fama-French 12 groups and reword SRS-02, SRS-10 and SectorAssignment. Option B: switch sector off now, tag SEC-01, SEC-02, VL-11 and the sector parts of the others "Must if built", and say "by sector, if available" in the reports. John decides.

**I-03 Consensus-only baseline cannot exist on the free route (N4).**

Market N4 is a Must need: compare with "a tabular-only baseline and a consensus-only baseline". FR-06 makes the consensus baseline conditional and prospective-only, and SV-07 returns "unavailable" for it. A test for N4 as written cannot pass for the 2023 to 2024 test set.

Affects: N4, FR-06, EP-07, SV-07.

Resolution: Reword N4 to "a consensus-only baseline where a consensus source exists", with the market document change approved by John.

**I-04 FR-07 and ER-04 describe a failure that cannot happen after decision C-15.**

FR-07 criterion 1 says that when an upstream API returns an error the response is 503 naming the failed source. ER-04 and SV-14 say the same. C-15 and SV-01 say a lookup reads stored predictions and never calls a source. The only things a request touches are PostgreSQL, Redis and the stored explanation. The sources are called by scheduled jobs, which retry (PL-02).

Affects: FR-07, ER-04, SV-14.

Resolution: Redefine the trigger. For example: 503 when PostgreSQL or Redis is unavailable, and a warning in the envelope when ingestion is stale (PL-03). John approves the new wording.

**I-05 Where does explanation job state live, and who may write it.**

FR-19 and SV-06 say the API creates a job and returns an id within 500 ms with status pending. DB-02 gives the API a read-only role. DB-01 says Redis holds no project data of record, and ADR 0001 says the result store is not a durable record. Product Section 11 puts `job_status` in the Explanation table in PostgreSQL. So no role can create the pending row at request time, and EP-05 for an unknown id has no defined answer.

Affects: FR-19, SV-06, EP-04, EP-05, DB-01, DB-02.

Resolution: Decide one of: the API role may insert only into the explanation job table; or the job id is the Celery task id and status comes from the result backend until the worker writes the row. John decides under D-38.

**I-06 ER-13 says the system "raises an alert", and no alert exists.**

No requirement defines an alert channel. D-13 and ET-04 are about removing or restricting alerts. DP-09 allows no paid monitoring.

Affects: ER-13, SV-08.

Resolution: Reword to "logs at error level and /health reports the artefact failure" (SV-08 already requires the second part).

### Group 2: cannot be tested as written, or may not be satisfiable

**I-07 NFR-04 and NFR-03 have no measurable pass line.**

NFR-04 (Must) says "best effort; no SLA", so nothing can fail. NFR-03 says new transcripts are available within 24 hours of publication, but the sources give no publication time (Alpha Vantage first-publication timestamps are unverified, Data Section 4), the Hugging Face set is a static snapshot, and the free Alpha Vantage key allows 25 requests a day (IG-07).

Affects: NFR-03, NFR-04, PL-03.

Resolution: NFR-04: reword to a checkable statement (for example /health answers 200 in the Compose build) or drop it. NFR-03: measure against the ingestion job's own check time, not the source's publication time.

**I-08 The corpus size in the SSOT does not match its own scope.**

SSOT Section 4 says S&P 500 companies, 2015 to 2024, "about 4,000 to 5,000 earnings events". 500 companies times 40 quarters is about 20,000. 100 companies times 40 quarters is about 4,000, which matches decision C-18, not the S&P 500. TX-04 (90% of "target events, S&P 500 2015 to 2024"), NFR-09 (backfill of 4,000 to 5,000 events) and the Product Section 16 milestones depend on which is meant.

Affects: TX-04, TX-07, NFR-09, IG-21, IG-22.

Resolution: John states whether the target corpus is the 100-company subset (widened if time allows) or the full index. The SSOT is owner-only, so I only propose wording. Until then I would test TX-04 against the loaded universe.

**I-09 FR-25 and MD-20 may run but show nothing.**

They look for a jump in the sentiment and outcome relationship at FinBERT's pretraining cutoff (D-22, unknown) using a checkpoint that is not yet chosen (D-35). A label needs at least 10 quarters of EPS history (LB-02), so the first usable label is around 2012 even though the transcripts start in 2005. If the cutoff is earlier than about 2012, there is no labelled data on the before side and the test cannot show a jump. I have not verified the cutoff or the checkpoint.

Affects: FR-25, MD-20.

Resolution: Decide D-35 and D-22 first, then check that the cutoff lies inside the labelled range. If it does not, reword FR-25 to say so, and report the series anyway.

**I-10 Pass lines that real data may fail, or that are not set.**

LB-06 and VL-06: one frozen threshold pair must leave no class under 10% in any year, which is a property of the data and can fail (it is marked proposed). TX-04: 90% transcript coverage, while the spike in Data Section 12 found three of three removed companies ending in 2021 or earlier. VL-05 needs a gap threshold, and TH-06 says it is to be set after the first run, so there is no pass line yet. VL-08 wants 20 widely reported surprises (public records are consensus based) to land in the expected class under the time-series label, and LB-08 exists to measure how often the two labels disagree, so 20 of 20 can fail without a defect. AE-02 wants 98% agreement with a second source (yfinance), but LB-07 says that source is usually adjusted EPS while the label uses diluted EPS, so basis (AE-03) has to be settled first.

Affects: LB-06, VL-06, TX-04, VL-05, VL-08, AE-02.

Resolution: These stay as measurements. For each, agree what happens if it fails (narrow the scope under SR-06, report the limitation, or change the threshold under D-06). VL-05 needs TH-06 set. VL-08 should name its label route.

**I-11 FR-27 cannot be confirmed implementable.**

It asks for the same features and split rules on FinCall-Surprise. The features need EDGAR EPS history, fundamentals and prices, and I have not seen the dataset's fields (Data Section 14 says the LICENSE file was not opened, D-24). The paper's own post-call label also differs from ours.

Affects: FR-27, SM-02.

Resolution: Inspect the dataset's fields and licence (D-24). If tabular features cannot be built, restrict the replication to text features and say so, or drop it. It is Should and early in the drop order (PD-06).

**I-12 Requirements only a person can satisfy.**
